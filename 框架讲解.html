框架讲解

框架必备

一、元件树和开机

1.1 machine.xml 的样子

后端装哪些设备、怎么接线，全写在机型的 machine.xml 里。一个 Setting 节点就是一个元件：Type 写元件类的全名，Value 是它的参数，里面的 Setting 是它的子元件。启动代码里不 new 具体元件，换机型只换这个文件。

写法意思
<Setting Name="…" Type="…">一个元件。装配时按 Type 找到类，new 一个
不写 Type 的 Setting分组节点：不生成元件，名字照样进路径。下面的元件没有父元件，算根元件
<Value Name="…" Value="…" />参数，对应元件类上带 [Machine] 的同名属性，名字不分大小写
Setting 里的 Setting子元件，挂在外面那个元件下面
InitOrder="…"开机准备的先后，越小越先，不写是 10000（35021 没用）
  • 35021：220 个 Setting、665 个 Value。顶层 26 个节点，其中 7 个是分组节点（Database、Monitor、LoadPort、Robot、Chamber、CDS、Supply），一共装出 31 个根元件（1.7 的开机日志）。
  • 文件读进来是三个类：根 MachineSettings、节点 ModuleConfig、参数 ValueConfig。

1.2 找到 machine.xml

程序里不写死 machine.xml 的路径：运行目录有个 Paths.json，ConfigPath 指 machine.xml 所在的目录。ec.xml 和 GEM 编号表也放在这个目录。

  • 没有 Paths.json、没配 ConfigPath、目录里没有 machine.xml，这三种情况开机直接失败，托盘红灯。
  • Paths.json 在 xyz.Configs 工程里，宿主编译时拷到输出目录（xyz.GrpcHost.csproj）。machine.xml、IO 点表是机型的，机型工程编译后部署进宿主的 Config 目录（xyz.GrpcHost.csproj）。
  • machine.xml 只在开机读一次（ServiceExtensions.cs），改了要重启。运行中往回写的只有 MachineLoader.SaveValue，现在只有切晶圆尺寸用（MachineLoader.cs）。

1.3 认类：[Element]

Type 只是一个字符串。装配器开机先把运行目录里所有标了 [Element] 的元件类登记成一张表，再按 Type 查表。机型的 DLL 不用宿主引用，拷进 Modules 目录就认得出来。

  • 登记的名字是 [Element] 的 Key，没写 Key 用类的全名（ElementAttribute.cs）。现在 75 个元件类都没写 Key，machine.xml 的 Type 一律写类全名。
  • 例子：LoadPortModule.cs 标了 [Element(description: "35021 LoadPort 模块（富创得 LP300）")]，machine.xml 里写 Type="xyz._35021.Module.Loadport.LoadPortModule"。
  • Type 写错、或者机型 DLL 没部署进去，开机抛"未找到元件类"（ElementLoader.cs）。改了机型代码要跑 tools\deploy-module.ps1。

1.4 装树、灌参数

装配器从上往下走配置树：有 Type 的 new 一个元件，定名字和全路径，先给所有 [Machine] 属性灌默认值，再用同名 Value 覆盖，最后挂到父元件下面，接着装它里面的节点。

  • 全路径照 machine.xml 的层级拼，分组节点的名字也算：LoadPort.LoadPort1.Carrier、Chamber.Chamber1.Door。报警按它算在哪个模块头上，日志的两层名字也从它来（ElementLoader.cs）。
  • 参数名写错：记一条错误日志，那一项留默认值，照常开机。值转不了类型（比如 bool 写成 yes）：抛异常，开机失败（ElementLoader.cs）。
  • 灌完参数调元件的 OnSettingLoaded，把整个节点交给它，读名字不固定的配置（比如工艺配方的字段表）用。
  • 整棵树装完，虚拟 IO 点统一核一遍（ElementLoader.cs）。

参数名写错，ElementScanSmoke 里的一条：

【2026-10-29 11:26:18.319】 【ERROR】 【Host】 machine.xml 节点 TypoGroup.Typo 的参数 IsRunn 不认识：ScanProbe 没有这个参数（名字写错了，或者参数已经删了），这一条没用上

1.5 进容器：[Ioc]

树装好以后，每个元件按它实现的、打了 [Ioc] 的接口登记进 IoC 容器，别处用 IocHelper.GetService<接口>() 取。没打 [Ioc] 的接口不登记：阀、DI、轴、载具这类部件进不了容器，只能由父元件在自己下面找（1.9）。

  • 打了 [Ioc] 的接口现在 50 个，都是全机一份的服务和模块：IAlarm、IEc、IRecipeElement、ILoadPort、ISupplyAccess……。ICarrier、IAxis、ICarrierIdReader 没打。
  • 登记成单例，但实例是装配器 new 的：容器不建、也不释放，开机、退出照旧由装配器管。
  • 同一个接口有好几个元件实现（两个 LoadPort 都是 ILoadPort）：GetService 拿最后登记的那个，GetServices 按 machine.xml 先后拿全部。
  • 登记在宿主 Build() 之前（ServiceExtensions.cs），那时容器还没建好，所以元件的构造和 OnSettingLoaded 里不能取别的元件，要取放到开机的 Bind（1.7）。

1.6 开机前：查必配、合 EC、编号表

容器建好以后（Program.cs），先做三件框架的事，再进开机五步。

做什么说明
接上容器后面每个元件都靠 IocHelper 取别的元件
查 System、Mapper、Log、Alarm、Io、WaferSize 六个节点平台离不开它们，没配就抛异常（ServiceExtensions.cs），开机失败
合并 EC照元件树把 ec.xml 补全。元件开机准备时就要读 EC，所以排在五步前面；没配 EC 节点只记一条警告，EC 全按代码默认值走
编 GEM 编号表SV、DV、EC、报警、事件五张表，跟 machine.xml 放同一个目录；E30、EDA、数据曲线用

1.7 开机五步

元件自己的开机准备都写在五个钩子里，装配器按固定顺序挨个调。启动代码只调这五个，不点名任何具体元件，加元件不用改它。

步调谁、什么顺序元件在这里做什么
1 InitElement根元件按 InitOrder；每个元件再按 InitOrder 调子元件（ElementBase.cs）开机准备：连通道、读点表（IoElement.cs）、认自己的子元件。不动硬件；动硬件的叫 InitModule，比如 LoadPort 的就是 Home（BaseLoadPortModule.cs），人或整机初始化才调
2 Bind整棵树按 machine.xml 先后，父先子后取别的元件、存成字段（腔体取配方库、整机、供液）
3 StartScanning只对配了 IsRun 的根元件各起一条扫描线程（扫描线程那一章讲）
4 OnStarted同 Bind要等扫描都跑起来才做的事
5 PublishOnStartup同 Bind；一个抛异常只记错误日志，后面照做推界面一连上就要拿到的状态（gRPC 通讯 4.10）

宿主 10-28 开机日志里的汇总：

【2026-10-28 14:55:35.940】 【INFO】 【Host】 根元件装配 31 个，模块 8 个，启动独立扫描 16 个：System, Plc, Io, Safety, Computer, DataChart, RealChart, LoadPort.LoadPort1, LoadPort.LoadPort2, Robot.Robot1, Dispatch, Chamber.Chamber1, Chamber.Chamber2, Chamber.Chamber3, Chamber.Chamber4, CDS.IPA
  • "整棵树按先后"是 Walk 走的：父在前、子在后，IsEnabled 为 false 的连同下面一起跳过（ElementLoader.cs）。
  • InitElement 返回 false（比如驱动没连上）只记一条错误日志，开机接着走（ElementLoader.cs）。
  • 五步的先后、一个出错不耽误后面，ElementScanSmoke 里都有检查（ElementScanSmoke/Program.cs），在仓库根目录跑 dotnet run --project tools\ElementScanSmoke。

1.8 退出

退出分两步：先挨个停每棵树的扫描，再按开机的倒序调 OnStopping。停扫描只等手上这一拍扫完，每棵最多等 2 秒，写死在 ElementBase。

  • 宿主停下时（托盘点退出）调它（Program.cs）。
  • 先停扫描：收尾要断链路、落库，扫描还在跑就会撞上；宿主随后还要释放容器，扫描里再取报警、EC 会报"对象已释放"（ElementLoader.cs）。
  • 只等手上这一拍：扫描线程每拍扫完歇 10 ms 再看停止标记（ElementBase.cs），正常几毫秒到十几毫秒就停了。没起线程的根元件不等；在自己的扫描里停自己也不等，不然会卡住。
  • 2 秒是常量 StopScanWaitMs = 2000（ElementBase.cs），machine.xml 和 EC 都改不了。注释的理由：一拍正常几毫秒、慢扫描报警线 300 ms，等 2 秒够了；卡死的不等，免得宿主退不掉。
  • OnStopping 里做断链路、落库、存盘这类收尾（ElementBase.cs）。

二、扫描线程

2.1 三种线程

后端跑起来之后只有三种线程在动设备。看懂这张表，后面所有"为什么这段代码写成这样"都有答案了。

线程有几条谁起的干什么
扫描线程35021 是 16 条开机第三步 StartScanning设备的事全在这上面做：读 IO、推动作、推状态
RPC 线程来一个调用一条gRPC 宿主只做两件事：调动作入口、等动作到终态。不碰设备
接收泵每条连上的通道一条FrameCommunication.cs只管从串口／网口收字节、拼成一帧放下，不解释内容

另外还有两条跟设备无关的：数据曲线的写库线程 DataChart.Writer（DataChartElement.cs）和托盘图标的消息循环（HostTrayIcon.cs）。

一条规矩贯穿全框架：设备的事只在扫描线程上做。这样每个元件的状态只有一条线程在改，绝大多数地方不需要加锁。

2.2 谁起线程：IsRun

不是每个元件都有自己的线程。只有 machine.xml 里写了 IsRun 的根元件才起一条，它下面的子元件跟着它一起扫。

35021 开机日志那一行就是答案：

  • 16 条线程背着 189 个元件。两个 LoadPort 各一条、互不影响；但 Chamber1 下面的腔门、摆臂、8 个喷嘴、一堆 DI 全挤在 Chamber1 这一条上。
  • 8 个模块都是根元件，所以每个模块的动作都在它自己那条线程上推（见 2.5）。
  • 子元件不要单独调 Start()——它已经在父元件的扫描里了，再起一条就是同一个元件被两条线程扫。

起线程那一行有个保护：

CompareExchange(ref x, 1, 0) 的意思是"x 是 0 就改成 1，不管改没改都返回原值"。第一次调返回 0，往下走起线程；第二次返回 1，直接 return。

  • 写成 if (已经起过) return; 已经起过 = true; 不行——那是两步，两条线程可能都读到 false、都往下走，起出两条线程扫同一棵树。Interlocked 把"读 + 比 + 写"合成一条不可分割的 CPU 指令。
  • 用 int 不用 bool，是因为 Interlocked.CompareExchange 没有 bool 的重载。
  • ElementScanSmoke 里拿 20 条线程轰它，断言只出现过 1 条线程号（ElementScanSmoke）。

2.3 一拍

扫描线程就是个死循环：扫一拍、歇 10 ms、再扫一拍。

  • 遍历是框架做的。ScanOnce 不是 virtual，谁都改不掉——元件作者不需要、也没办法管"子元件怎么扫"。
  • 每个元件各自计时、各自接异常。一个部件抛异常，它的兄弟和父元件这一拍照跑。
  • 10 ms 是"扫完再歇 10 ms"，不是"每 10 ms 一拍"。实际周期 = 这一拍耗时 + 10 ms。一拍跑了 50 ms，这一轮就是 60 ms。
  • ScanOnce 是 public：冒烟测试不起线程，手动打一拍用的就是它。
  • TaskCreationOptions.LongRunning 让扫描线程拿一条专用线程，不占线程池。

2.5 动作驱动：IRoutineHost

模块身上还挂着动作。动作推进不占用 OnScan，它是一种独立的能力：

BaseStateElement（所有模块和整机的基类）实现它：

三层分工，名字容易混：

层方法含义
元件OnScan()这个元件这一拍做什么
动作ModuleRoutine.Scan()这个动作往前走一格
步骤RoutineStep.Run() / Check()这一步发指令 / 查做完没

调用链：框架 ScanOnce → IRoutineHost.StepRoutine → 动作.Scan() → 步骤.Run()/Check()。

"走一格"具体是什么：

所以一拍里是三种情况之一：第一次进这一步就 Run() 发指令（发完就走，不等）；这一步在等就只 Check() 一下；刚好好了就 _index++，循环不 return，接着把下一步也发出去——一拍可以连走好几步，只要它们都是立刻完成的。

一步等 480 ms，就是被 Check() 查了 48 拍，这期间整条扫描线程照常在跑，别的元件一拍都没少。

到终态的收尾，四步顺序是定死的：

  • _routine = null 在 finally 里：回调抛异常也要清掉，否则这个模块以后永远"忙着"、再也接不了新动作。
  • NotifyCompletion() 唤醒的是在 WaitReply 上等着的 RPC 线程——界面那次点击才等得到回包。

为什么做成接口、不占 OnScan：动作推进是"挂得住动作"这类元件的能力，不是"这一拍做什么"的一部分。分开之后模块的 OnScan 只剩自己的活，继承链上一个 base.OnScan() 都不需要。跟 IPlcBlock、ITransferRobotStep 一样，是可选能力做成接口、调用方 is 判断的路子。

2.6 慢扫描：200 / 300

一拍扫太久要报出来，否则设备"反应慢"这种事查不到根。阈值分两档。

模块和两个管理器把阈值接到了 EC 上，现场能在线调：

  • 接了 EC 的：所有模块（BaseStateElement.cs）、Job 管理（JobManager.cs）、搬运管理（TransferManager.cs）。其余元件用默认的 200 / 300。
  • 因为是每个元件各自计时，日志能直接指到具体部件——【Chamber.Chamber1】【Arm1.Nozzle_SC1】慢扫描报警 420ms，而不是笼统记在 Chamber1 头上。

2.7 扫描线程里不等待

这条是前面所有内容的推论，但值得单独写出来，因为它是最容易写错的地方。

在哪条线程能不能等为什么
扫描线程不能整棵树共用这一条。在这里 Wait 一秒，这棵树上十几个元件这一秒全部停拍：状态不推、IO 不读、别的动作也不往下走
RPC 线程可以这条线程本来就是为这个调用开的，等完就回包
  • 扫描线程上的写法永远是：发出去就走，下一拍再看做完没有。
  • WaitReply 这种阻塞等终态的方法，只给 RPC 线程和冒烟测试用。
  • 所以界面上点一个动作，回包只说成没成；界面上看到的状态变化全靠推送，是扫描线程每一拍 PublishState() 发出来的。

2.8 停扫描

宿主退出时先把所有扫描停掉，再让元件收尾。顺序反了会出事。

  • 最多等 2 秒（StopScanWaitMs）。一拍正常几毫秒、慢扫描报警线才 300 ms，2 秒足够；卡死的不等，免得宿主退不掉。
  • 在自己的扫描里停自己不会卡：比对 _scanThreadId，是自己就直接返回，循环下一次判断 _scanStopping 时自己出来。整机"全部停止"这类动作会用到。
  • _scanStopping 是 volatile 的——改它的是别的线程，扫描线程每一拍都要看见最新值。

3.1 动作是什么

设备上"点一下按钮让它干件事"——开门、回零、取片、跑工艺——在这套框架里统一叫动作。

一个动作 = 一串有名字的步骤 + 一个状态。35021 的 LoadPort 装载（Load）建出来是 4 步：

它自己不会跑，要靠模块的扫描线程每 10 ms 推一格（第二章 2.5）。为什么不写成 await 开门(); await 扫片(); 那种直观写法：扫描线程一等就卡住整棵树，这棵树上还挂着别的设备。

做成这个形状，换来三件事：

  • 出事知道停在第几步——日志里直接是 失败在 3/4 取槽图，不用加日志重现
  • 急停能按步收场——正在等的那条指令会被作废，否则复位之后同一条指令发不出去
  • 换品牌只改机型层——平台定骨架、机型填品牌指令

一、总览

1.1 三种调用

调用用在哪契约返回什么时候结束
一元调用按钮、查询、读设置（绝大多数接口）Task<RpcResponse>回一条就结束
服务端流：事件流后端把变化推给界面，每台客户端开机开一条IAsyncEnumerable<EventMessage>不结束，断开才关

二、远程调用原理

2.1 契约就是 C# 接口

用的是 protobuf-net.Grpc 的 code-first：不写 .proto 文件，直接拿 xyz.Shared 里的 C# 接口当契约。接口标 [ServiceContract]，方法标 [OperationContract]，客户端和后端编译的是同一个接口。

  • 请求地址由名字算出来：命名空间 + 接口名去掉开头的 I + 方法名去掉结尾的 Async，例如 /xyz.Shared.Services.LoadPortService/Load、/xyz.Shared.Services.EventService/Subscribe。
  • 返回类型决定调用种类：Task<T> 是一元调用，IAsyncEnumerable<T> 是服务端流。客户端流、双向流没用到。
  • CallContext 是这次调用的附加信息：客户端用它带取消令牌、截止时间（开机问语言给 3 秒，App.xaml.cs）；后端从 context.CancellationToken 知道对面断了，事件流和导出都靠它收尾。
  • 能直接编成字节的类要标 [ProtoContract]，整个框架只有三个：RpcRequest、RpcResponse、EventMessage。DTO 都不标，先转成 JSON 字符串，装在这三个类的字段里。

2.2 客户端调的是替身

客户端拿到的服务对象不是后端的服务，而是 protobuf-net.Grpc 在运行时照接口生成的类（替身）。它实现同一个接口，方法里只做两件事：把调用编成网络请求发出去，把回来的字节还原成对象。

探针照 RemoteEventConnection.cs 的写法连事件流，后端没开时的输出（探针不在仓库里）：

service 的真实类型：ProtoBuf.Grpc.Internal.Proxies.ClientBase.IEventService_Proxy_0
  所在程序集：ProtoBuf.Grpc.Internal.Proxies-1，运行时现生成的：True
本进程里找不找得到后端的 EventService 类：False
SubscribeAsync() 立刻返回了，拿到的序列来自程序集：protobuf-net.Grpc
开始取的时候出错：RpcException：Status(StatusCode="Unavailable", Detail="Error connecting to subchannel.")
  • 客户端进程里没有后端代码。service.SubscribeAsync() 是往后端端口发请求，后端收到后自己调 EventService.SubscribeAsync。
  • 客户端代码只认接口：DataCenterSmoke 把后端的 DataChartService 对象直接交给客户端的导出代码（DataCenterSmoke/Program.cs），不走网络也能跑。

  消息    [1 字节][4 字节长度][RpcResponse 的字节]    一元调用只有这一条

  • 每条消息前 5 个字节：压缩标记 + 长度。对面按长度切出一条，事件流上连着来几千条也不会粘在一起。
  • 消息体按 [ProtoMember(n)] 的编号排。默认值（空串、0、false）不写，所以客户端收到的空 token 可能是 null，收的时候先归一成空串（RemoteEventSubscriber.cs）。
  • 一元调用回完一条就发结尾；事件流一直不发结尾，所以一直开着。

4.1 整条路

4.3 黑板

黑板是一张表：键是（消息类型全名, token），值是这一格最后一封信。名字借的是 MQTT 的保留消息（retained message），所以字段叫 Retain、类叫 RetainedBoard。

  • 为什么每次 Send 都要写：模块是"变了才推"，后端不知道客户端什么时候连上。08:00 推的 LoadPort1 = Idle 当时没人收；不记下来，08:30 打开的客户端要等到 LoadPort1 下次变化（可能几小时）才有东西显示。
  • 每种状态一格、只留最后一封，不会越攒越多。通知类不写，还把同一格擦掉。

4.4 两块黑板

4.5 收件人名单

  • _sentListeners（RemoteEventPublisher.cs）一项 = 一台连着的客户端。EventService 每开一条流登记一项 message => channel.Writer.TryWrite(message)（EventService.cs），流断了用凭据删掉。
  • 为什么每次抄新名单：Send 在锁里只拿走名单，出了锁再遍历。名单换上去以后没人再改它，遍历时有客户端连上或断开也不影响，不会报"集合已修改"。
  • 客户端那边对应的是 Handlers：一项 = 一个页面的一次 Register（客户端代码里 35 处）。后端不知道页面订了什么，每台客户端收到的都一样。

4.7 客户端收

  • 开机在界面线程上调一次 Initialize()（App.xaml.cs），记下界面线程，Task.Run(RunLoop)（RemoteEventConnection.cs）。
  • 收到任何一条都 SetConnected(true)，只有第一条真改状态（RemoteEventConnection.cs）。开流标记不往下交；别的交到界面线程给 Deliver（RemoteEventConnection.cs）。
  • 后端没起、退出、网断（抛异常），或者流正常结束：标记断开，等 3 秒重开，后端会再重放一遍黑板。
  • 顶栏蓝灯就是 IsConnected（MainWindow.xaml）；断开时红黄绿也一起灭（TopBarViewModel.cs）。

4.8 客户端分

  • 按（类型全名, token）分：同是 LoadPortDto，token 是 LoadPort1 的只给订了 LoadPort1 的页面；全局消息的 token 是空串。
  • 没人订的类型不拆，只记在小黑板上，等有页面订了再拆。
  • 同一格几个页面订（LoadPort1 有手动页、主界面、调度图），JSON 只拆一次，然后挨个回调（RemoteEventSubscriber.cs）。
  • 回调在界面线程上，页面直接改绑定属性。拆不开、回调抛异常都进 DeadLetter，不影响下一个。
  • Register 返回凭据，页面存成字段，销毁时 Dispose 退订。

4.13 实测：流上来的消息

探针连 EventBusSmoke 的 server 模式（另一个进程，里面是真的 EventService 和 RemoteEventPublisher）。它开端口前先发了 tick 0（状态类）和几条 notice（通知类），之后每 200 ms 发一对 live（状态类）、notice（通知类）（EventBusSmoke/Program.cs）。客户端收到：

+  119 ms 第 1 条：TypeName=""            Token=""       Payload=                              Retain=False   ← 开流标记
+  120 ms 第 2 条：TypeName="TickMessage" Token="tick"   Payload={"sequence":0,"token":"tick"}   Retain=True    ← 黑板
+  120 ms 第 3 条：TypeName="TickMessage" Token="live"   Payload={"sequence":2,"token":"live"}   Retain=True    ← 黑板
+  254 ms 第 4 条：TypeName="TickMessage" Token="live"   Payload={"sequence":3,"token":"live"}   Retain=True    ← 新发的
+  254 ms 第 5 条：TypeName="TickMessage" Token="notice" Payload={"sequence":3,"token":"notice"} Retain=False
+  454 ms 第 6 条：TypeName="TickMessage" Token="live"   Payload={"sequence":4,"token":"live"}   Retain=True
+  454 ms 第 7 条：TypeName="TickMessage" Token="notice" Payload={"sequence":4,"token":"notice"} Retain=False
  • 第 1 条是开流标记；第 2、3 条是黑板（live 1 已经被 live 2 盖掉）；连上之前的 notice 一条都没来。
  • 之后 live、notice 混在同一条流上，客户端只调了一次 SubscribeAsync。
  • EventBusSmoke 每次都自动查这些（34 项）：连上先重放黑板、连之前的通知不补、按 token 分、后端停了报断开、回来 3 秒内重连并再重放（EventBusSmoke/Program.cs）。

5.1 为什么分段

数据曲线页把一段时间的原始数据导成 Excel。数据量一条消息装不下，所以用有尽头的服务端流：后端一小时读一段、回一条，客户端收一段写一段。

时间段（1 秒一行、20 条曲线）行数JSON 大小
1 小时3,600约 0.7 MB（DataChartElement.cs）
1 天86,400约 17 MB，超过客户端单条上限 16 MB
1 周约 60 万约 118 MB
要求做法
每条消息不能太大1 小时一段，一段一条回包
两头内存都不攒整份后端读一段给一段；客户端 Excel 写到哪行才去取哪行
有进度每收完一段，按这段最后一行的时刻报一次
能取消一个取消令牌，同时停掉客户端的读取和后端的读库
失败不毁原文件先写 .tmp，写完再换上；失败删掉临时文件
  1. 界面选文件、弹进度条（带取消），后台线程调 ExportAsync。
  2. 后端找出时间段里的日表（一天一张），每张按 1 小时切段，读一段 yield return 一条。
  3. 客户端把每段摊成行，MiniExcel 一天一张表往 .tmp 里写，写到哪行才去流里取哪行。
  4. 没有下一段：后端 yield break，这一路结束；客户端写完，把 .tmp 换成正式文件。

5.2 契约

  • 跟事件流一样返回 IAsyncEnumerable，区别是有尽头：段读完了序列就结束，这一路就关。
  • 每个元素是 RpcResponse：成功的 Data 装这一段的 JSON；失败的 Success = false 带错误码，跟一元调用一个处理法。
  • 请求参数：Start、End（本机时间）、Names（曲线名）。

5.6 写得慢会怎样

不会。导出从头到尾是往回拉的：Excel 要下一行才去 Rows 要，Rows 用完一段才去流里取下一条。

  1. 后端 yield return 一段，框架把它写到这一路上，写完才回来要下一段。
  2. 客户端不读，HTTP/2 流量控制让后端的发送窗口用完，这次写就停住。
  3. 写没完成，框架不来要下一段，Next 也就不去读下一小时的库。

所以同一时刻在路上的只有一两段。事件流正好相反：发的一方说了算，中间有筐，对面慢了筐会一直涨（7.1）。

1.1 五层，平台占四层半

一台设备从物理线路到业务代码，中间是五层。平台包了下面四层，机型只写最上面一层半。

三、平台：帧层

3.1 IFrameCodec：机型要实现的第一样

  • 一条通道一个实例：IFrameCodec.Extract 要靠上一段剩下的半帧，两条通道共用一个实例会把字节搅在一起。
  • 二进制协议把 Encoding 写成 Encoding.Latin1：0x00–0xFF 跟 U+0000–U+00FF 一一对应，字节过字符串管道不丢。整条链路内部是用 string 传帧的，这是代价最小的做法。
  • IFrameCodec.Decode 认不出来返回 null，通道记一行"解不出来，丢掉"，不抛异常。

3.2 IFrameLink / LinkStep：要握手的协议

有些老设备不能直接发数据，要先问一声（ENQ → EOT → 数据 → ACK）。这种协议不用在每条指令里写握手，把 IFrameLink 一起实现在解码器上，通道照它收发。可选，没有握手的协议不实现。

LinkStep.Rejected 这一项很实用：对方回 NAK 就让在途指令立刻落失败，不用白等超时。

3.3 FrameCommunication：接收泵和 PumpSession

FrameCommunication 把传输和解码器粘在一起，对上只有一个事件 MessageReceived(帧原文, 解好的报文) 和 Open / Close / Send(帧体)（接口是 IFrameCommunication）。

接收是一条 LongRunning 线程的死循环。麻烦在于：断线重连时，旧泵可能正卡在 Receive() 里，等它醒过来新连接已经起来了。如果用一个全局"在收"标志，旧泵退出时会把新连接一起关掉。所以每次 FrameCommunication.Open 新建一个 PumpSession，泵只认自己那一轮：

  • 发的那一头 FrameCommunication.Send 用 _sendGate 串行化，多线程调安全。
  • 解码器抛异常、订阅方抛异常，两种都不会弄死泵。

③ 解析队列（Channel<Received> + 一个 RouteAsync 任务）：接收泵只管入队就走。DeviceDriver.Route 的顺序是——解不出来的记一行丢掉 → 先给链路层（握手自己消化，Rejected 就 AbandonAll）→ 挨个问在途指令 Accept → 谁都不认就当设备主动上报：

5.5 平台给的三个复用件

① RfidReaderElement<TReadCommand>：读码的非阻塞步进机，实现 ICarrierIdReader。装机参数 IdStart / IdLength，EC ReadCarrierIdTimeout。RfidReaderElement.StartReadCarrierId 发了就返回，RfidReaderElement.OnScan 里推进，RfidReaderElement.GetCarrierIdResult 取走就清。机型只填三个抽象方法：CreateCodec、CreateReadCommand、CarrierIdOf。

② StatusQueryLoop：状态轮询的节奏器。一圈一圈查、同时只有一条在途、超时作废接着查下一条、一圈查完离这圈开始满一个周期再开下一圈。模块给它一个 Func<IEnumerable<DeviceCommand>>（每圈重新取一次），yield return 一条 = 替我发出去、等它回来或超时。StatusQueryLoop.Scan 返回 StatusQueryEvent（None / TimedOut / Disconnected），查到的值由模块自己在 QueryDataLoop 里写。它发的指令自动带 IsPolling。

③ CommandStep：ModuleRoutine 里的一步 = 发一条指令等设备回。

CommandStep.Waiting 对外报"在等设备回 CLOAD"，界面上能看见动作卡在哪一步；CommandStep.OnAborted 在动作被中止时作废在途这条。

8.4 第三个文件：解码器

解码器只管"字节怎么变成一条条报文"，不碰业务。拆帧一定要自带缓冲——串口、网口都可能一次只收到半行。

// ScanGunCodec.cs
using System.Text;
using xyz.Drivers.Communication;

namespace xyz._35021.Module.Drivers.ScanGun;

/// <summary>
/// 扫码枪解码器：一行一帧、回车结尾；自带缓冲，收上来多少接多少，收齐一行交一帧
/// </summary>
public sealed class ScanGunCodec : IFrameCodec
{
    private readonly StringBuilder _rxBuffer = new();

    /// <summary>
    /// 文本协议，ASCII
    /// </summary>
    public Encoding Encoding => Encoding.ASCII;

    /// <summary>
    /// 包壳：帧体后面加回车
    /// </summary>
    public string Wrap(string body)
    {
        return body + ScanGunProtocol.FrameEnd;
    }

    /// <summary>
    /// 拆帧：按回车切，最后那半行留着等下一段
    /// </summary>
    public IEnumerable<string> Extract(string chunk)
    {
        _rxBuffer.Append(chunk);

        string buffered = _rxBuffer.ToString();
        var frames = new List<string>();
        int index = buffered.IndexOf(ScanGunProtocol.FrameEnd);
        while (index >= 0)
        {
            string frame = buffered[..index].Trim('\n');
            buffered = buffered[(index + 1)..];
            if (frame.Length > 0)
            {
                frames.Add(frame);
            }

            index = buffered.IndexOf(ScanGunProtocol.FrameEnd);
        }

        _rxBuffer.Clear();
        _rxBuffer.Append(buffered);
        return frames;
    }

    /// <summary>
    /// 解报文：一行就是一条，ERR 开头是设备回的错
    /// </summary>
    public object? Decode(string frame)
    {
        return new ScanGunMessage
        {
            IsError = frame.StartsWith(ScanGunProtocol.Error, StringComparison.Ordinal),
            Text = frame,
        };
    }
}
  • 二进制协议把 Encoding 换成 Encoding.Latin1，缓冲用 List<byte>，校验在 Wrap 里加、Decode 里验，整体形状照 FcdRfidCodec。
  • 认不出来的帧 Decode 返回 null，通道记一行"解不出来，丢掉"，不要在这里抛异常。

8.5 第四个文件：指令

// Commands\ScanGunReadCommand.cs
using xyz.Drivers.Device;

namespace xyz._35021.Module.Drivers.ScanGun.Commands;

/// <summary>
/// 触发一次扫码：发 TRG，设备回条码或 ERRxx
/// </summary>
public sealed class ScanGunReadCommand : DeviceCommand<ScanGunMessage>
{
    /// <summary>
    /// 在途键：这把枪一次只认一条，所有指令共用一个键
    /// </summary>
    public override string Key => "ScanGun";

    /// <summary>
    /// 读到的条码
    /// </summary>
    public string Code { get; private set; } = string.Empty;

    /// <summary>
    /// 组帧：壳（回车）由解码器包
    /// </summary>
    public override string BuildFrame()
    {
        return ScanGunProtocol.Trigger;
    }

    /// <summary>
    /// 收到一条：ERR 落失败，其余当条码落成功
    /// </summary>
    protected override bool Handle(ScanGunMessage message)
    {
        if (message.IsError)
        {
            Fail(message.Text);
            return true;
        }

        Code = message.Text;
        Complete();
        return true;
    }
}
  • 每条指令都必须走到 Complete 或 Fail，否则它永远占着在途位，同 Key 的指令再也发不出去（只能等调用方超时 Abandon）。
  • 回复分两步的设备（先 ACK 受理、再 INF 做完），收 ACK 时 return true 但不落终态，收 INF 才 Complete——照 FcdLoadCommand（6.3）。
  • 不是自己的报文 return false，平台会接着问别的在途指令。

8.11 接进去以后，谁来调它

这是新人最容易漏的一步：元件接进树里不等于有人用它。

情况谁调你要写代码吗
挂在 LoadPort 下面读载具号CarrierElement：它在载具到位后调 StartReadCarrierId，之后每拍 GetCarrierIdResult 取结果不用，接口对上就自动用起来
自己新加的设备（扫别的东西）用它的那个模块：开机时 FindChild<你的接口>() 取一次存字段，在 OnScan 或动作步骤里调要写，但只写调用那几行
整台设备就是一个模块模块自己：StatusQueryLoop 查状态、ModuleRoutine 里 CommandStep 发动作要写模块

LoadPort 认读头是按接口不是按类名——BaseLoadPortModule.InitElement 里一句 FindChild<ICarrierIdReader>()，所以换品牌、换成扫码枪，模块代码一个字不改。

8.12 扫一次码，四条线程接力

第几步在哪条线程干什么
1模块扫描线程RfidReaderElement.StartReadCarrierId：建一条指令、Send、马上返回
2同上DeviceDriver.Send 按 Key 占住在途位，帧进发送队列，记一行"发 TRG"
3发送任务DeviceDriver.SendAsync 取帧 → IFrameCodec.Wrap 包壳 → 写串口
4接收泵线程FrameCommunication.PumpLoop：读字节 → Extract 拆帧 → Decode 解报文 → 进接收队列
5解析任务DeviceDriver.Route：先给链路层，再挨个问在途指令 Accept，记一行"收"，都不认的当上报
6同上指令 Handle 取出条码、Complete()
7模块扫描线程RfidReaderElement.ScanRead 看见 IsCompleted 出结果；没回就比超时，超时 Abandon

扫描线程从头到尾没有一处在等：发了就走，下一拍再看回来没有（呼应 2.7 扫描线程里不等待）。所以你写的 Handle 是在解析线程上跑的，里面不能干慢活。

同一把枪换网口：machine.xml 子节点换成 TcpDriverElement、填 Host / NetPort，代码一行不改、重编都不用（只改了运行目录那份的话连编译都省了）。

8.14 设备不问自答怎么接

有些扫码枪是硬件触发或者自由扫描，不等你问就把码推上来。这种报文没有在途指令认领，DeviceDriver.Route 把它当"设备主动上报"丢给 Reported。接法还是不动平台，在机型工程写个元件订上它：

using xyz.Drivers.Communication;
using xyz.Elements.Attributes;
using xyz.Elements.Elements;
using xyz.Elements.Interfaces;

namespace xyz._35021.Module.Drivers.ScanGun;

/// <summary>
/// 自己吐码的扫码枪：不发指令，设备扫到就推一条上来
/// </summary>
[Element(description: "扫码枪（设备主动上报），下面挂一个通道节点")]
public class ReportingScanGunReader : ElementBase, ICarrierIdReader
{
    private ICommDriver? _driver;
    private IFrameCodec? _codec;
    private volatile string _code = string.Empty;

    /// <summary>
    /// 元件初始化（开机）：认下面的通道、交解码器、挂上报，再由基类初始化子元件
    /// </summary>
    public override bool InitElement()
    {
        var driver = CommDriverElement.FindIn(this);
        if (driver is null)
        {
            throw new InvalidOperationException($"扫码枪 {FullPath} 下面没有启用的通道节点。");
        }

        _codec ??= new ScanGunCodec();
        driver.UseCodec(_codec);
        driver.Reported -= OnReport;
        driver.Reported += OnReport;
        _driver = driver;
        return base.InitElement();
    }

    /// <summary>
    /// 设备推上来一条（解析线程上回调）：存下最近一次扫到的码
    /// </summary>
    private void OnReport(object message)
    {
        var scan = message as ScanGunMessage;
        if (scan is null || scan.IsError)
        {
            return;
        }

        _code = scan.Text;
    }
}
  • ICarrierIdReader 剩下四个成员照 RfidReaderElement 写（接口全文见 8.11）：这种枪没东西可发，StartReadCarrierId 直接返回 true，GetCarrierIdResult 把存下的码交出去、取走就清。
  • 交解码器一定要在 base.InitElement() 之前：通道是在它自己的初始化里连的，顺序反了会抛"没有解码器"。
  • 先摘后挂（-= 再 +=）：元件初始化可能重入，不这样会挂两份、一条报文处理两次。

9.2 跑起来了但不通：按这个顺序查

  1. 连上了没？ 主日志有没有"通讯断开，每 X ms 重连一次…"。有就是没连上：串口核 COM 号、有没有被别的程序占用（仿真器、串口助手）；网口先 ping、再 telnet 端口。连上会记一行"通讯恢复"。
  2. 发出去了没？ 主日志有没有"发"那一行。没有说明 DeviceDriver.Send 被拒——没连上，或者同 Key 的上一条还在途没落终态（Handle 里漏了 Complete / Fail）。
  3. 设备回了没？ 有没有"收"那一行。发了没收到：波特率 / 校验位 / 停止位不对，帧尾不对（Wrap 包错），设备那边没使能这条指令。
  4. 收到了但没人认？ 日志里是"（解不出来，丢掉）"就是 Decode 返回了 null；能解出来但指令没认（Handle 一直 return false），平台会把它当设备主动上报，这时候查对号规则（名字比对、消息 ID 比对）。
  5. 老是超时？ 三种可能：Key 选错（该一条一个键的用了共用键，前一条占着位）、Handle 里忘了落终态、超时 EC 给太短。

动作里的那一步失败时，错误码能直接定位：CommandRejected（指令被拒：没连上或同一条还在途）、DeviceFailed（设备回错，后面带设备给的原因）、Timeout（多少 ms 设备没回）——见 CommandStep（5.5）。

9.3 日志在哪、怎么看

文件里面有什么
宿主运行目录 Log\xyz-日期.log主日志：开机、连接断开恢复、报警、非轮询的收发原文
宿主运行目录 Log\poll-日期.log状态轮询（StatusQueryLoop 发的、带 IsPolling 的）收发原文，单独放免得刷主日志
  • 收发原文记在通道元件名下，日志行里有元件的两层名字，所以多台设备不会混。
  • 方向只有两个字："发" / "收"（LogHelper.Sent / LogHelper.Received）。
  • 日志按 KeepDays 自动清，别手工删正在写的那份。

9.4 写之前先扫一眼仓库规矩

接设备这一块常踩的几条（全部在 .claude\skills\xyz-framework\SKILL.md）：

  • switch 只写传统写法：case + return / break，不写 switch 表达式，case 里不写 or / when。
  • if 的大括号单独一行，单行也要带大括号；不写三元 a ? b : c。
  • 不写 x is { } y 这类花括号模式匹配，先取变量再显式判空。
  • 注释 /// <summary> 换行写一句短话再 /// </summary>，不写成单行。
  • 日志一律 LogHelper，不用 Console / ILogger / 直接 NLog。
  • 找元件一律按接口（FindChild<T>() / IoC），不写 X.Current 这种静态口子。

10.2 七个会踩的坑

  1. 通道必须是设备节点的直接子节点 —— CommDriverElement.FindIn 不递归，隔一层就找不到。
  2. 先 UseCodec 再 base.InitElement() —— 顺序反了通道连的时候没解码器，开机抛。
  3. 超时必须 Abandon —— 否则那条永远占着在途位，同 Key 的指令再也发不出去。平台写好的 RfidReaderElement、CommandStep、StatusQueryLoop 都做了这件事，自己写流程别漏。
  4. 一条通道一个解码器实例 —— 它自带拆帧缓冲，共用会把两边字节搅在一起。
  5. 定时查状态走 StatusQueryLoop —— 自己起定时器的话收发原文全进主日志，刷屏。
  6. 设备元件要挂在 IsRun="true" 的根元件下面 —— 子元件没有自己的线程，否则 OnScan 永不执行。
  7. 解析线程上的回调里不干慢活（Handle、Reported）—— 取个值就返回。
