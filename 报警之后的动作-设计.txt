================================================================================
报警之后的动作 —— 设计
2026-10-29
================================================================================

这份文档记的是"报警报出来以后，设备自己该做什么"的设计。
不含报警怎么定义、怎么上报 Host、怎么入库（那些已经做完了，见 skill 的 backend.md「报警」）。


================================================================================
一、背景：行业和两家参考代码怎么做的
================================================================================

【SEMI 标准管到哪里】

E5（SECS-II）规定报文：S5F1 报出 / 清除各发一次，带 ALID（编号）、ALTX（文本，≤40 字符）、
ALCD（一个字节）。ALCD 的 bit8 = 1 报出 / 0 清除，bit7-1 是分类：
    1 人身安全   2 设备安全   3 参数控制警告   4 参数控制错误
    5 不可恢复错误   6 设备状态警告   7 提示标志   8 数据完整性

E30（GEM）规定行为：每条报警只有 Set / Clear 两态；上电全清；除 S5F1 外每条报警还要有两个
CEID（going-on / going-off）；Host 可用 S5F3 单条关掉上报，且这个设置要掉电保存；
S5F5 / S5F7 供 Host 查当前报警和已启用报警。

★ 关键：标准到此为止。"报警之后设备停不停、关不关阀、Job 怎么办"一个字都没规定，
  全是厂商自定义。间接相关的只有 E10 / E116（报警引起的停机要落到状态模型）、
  E94（Control Job 的 pause / abort 语义）。

另一条行业共识：真正的人身安全不靠上位软件。急停、门互锁、光幕走硬件安全回路或安全 PLC
（SEMI S2、ISO 13849），ms 级断电断气。上位软件里的"人身安全类报警"只是事后知情 + 收场，
不是防护手段。


【JK（JKBase，C++ 老 CTC/PMC 平台）】

实现在 Library\JSeqCon\JSeqCon.cpp。三条互不相干的路：

1. 报警定义在配置。Alarm.cfg -> 每模块三个文件 .Alarm(LEVEL 2) / .Warn(1) / .Intlks(3)：

       000 COT1_000{
         "[COT1-ALM] EthCAT Communication error."
           RETRY  "Retry Operation = > RETRY"
           ABORT  "Abort Operation = > ABORT"
           IGNORE "Ignore Operation => IGNORE"
           LEVEL  2
       }

   三个级别直接映射 SEMI ALCD 的 3 / 4 / 5（ID_Handling.cpp:134）。
   级别只用来界面上色，不驱动任何动作。

2. 报警后的动作 = 原地问人。两种报法：JAlarm_Post 只登记不等；JAlarm_Manage 阻塞，
   0.5 s 轮询等操作员点按钮。动作全写在调用处的 if 里（JSeq_Macro.h 的标准套路）：

       while(TRUE){
           ...动作失败...
           alarm_result = JSystem_Alarm_Manage(...);   // 卡在这儿等人
           if      (ABORT)  return false;   // 例程失败返回
           else if (IGNORE) break;          // 当成功，往下走
           else             continue;       // RETRY 重做
       }

   JAlarm_Handle 本身只写个值 + 记日志 + 出队，不做任何自动动作。
   所以"IGNORE 是什么意思"每处自己定：气缸 IGNORE = 当它到位了，机械手 RETRY = 先复位再重试。

3. 真正的自动动作在互锁表 Intlks\<模块>\Value.int，每扫描拍判一次：

       if (COT1_VacSts==Normal && COT1_VacCtrl==On && COT1_VacSns==Offed && COT1_SpinVel > 2720) {
           $action = COT1_VAL_OFF;                   // 动作组：关 13 个阀 + 停 3 个泵
           $abort  = SCHEDULER_PROCESS_[COT1];       // 中止这个腔的工艺例程
           $event  = COT1_SPINMTR_CONTROL|SPINSTOP;  // 给设备发命令：停转
           $alarm  = COT1|ILK|002;                   // 报警
       }

   整机级的 ALL_VAL_OFF 一把关掉全部腔的阀和泵。
   实际配得很保守：中止按钮配了 $event = SCHEDULER_ENGINE|ABORT1 中止作业；
   10 路漏液只关对应那组阀 + 报警，不中止作业、不停整机（报警文本写着
   "System Abort if Running"，规则里没配 $abort）。

还有第四条半路：Parameter\EnvChk.cfg，传感器 -> 报警 + 置模块的 xxx_EnvSts 位，
工艺在 READY 和每片开工前查这个位，查到就原地等人。这是挡下一片，不打断正在跑的。
样例机台这张表只有表头、没配行。

没做的：报警自动暂停（PAUSEBYALARM 无人调用）、灯塔线程只有声明、弹窗"重试"按钮是坏的
（alarm_point 写死 -1）。模块没有 Error 态 —— 腔体出错就是例程卡在那儿等人，期间别的腔照跑。


【CTC（MECF / Aitex）】

（代码本机已被清理，以下是 2026-10-08 / 10-15 / 10-17 / 10-22 几次读的记录）

CTC 的思路跟 JK 相反：不问人，按配置自动收场。每条报警带一个 ActionString，
腔体报警写死了这几档：

    全停                  所有腔中止 + 停 CSM 供液柜 + 关供液阀
    本腔停                只停这个腔
    中止后冲洗再下线      跑 RCM 冲洗救片，再把腔下线
    做完这片再下线        不打断在制片
    提示                  只报不动
    jobstop / jobabort    作用到 Job 层

机制是接通的，但出厂几乎没配 —— 这是 CTC 的典型毛病：能力有、现场没用起来。

分层上 CTC 比 JK 清楚：
  - PLC 侧：分级报警数组（AllStop / ChamberStop…）+ 心跳超时，直接 Abort、停 CSM，不经上位
  - 上位软件：超差类报警（流量偏离设定 ±% 持续一段时间 -> Warning / Alarm）；
    排风、腔压超限只在空闲时让腔下线，不打断正在跑的片
  - 整机：三色灯（SignalTower.xml）是唯一真正汇总全部模块 IsError 的地方，
    System 状态格反而不汇总

CTC 另外两条值得学：中止后冲洗救片、Host 中止 PJ 走跳步回片（腔里的做完当前配方再回）。


【我们的现状（改之前）】

AlarmElement 只管四件事：当前报警表、人工复位、入库（按天分表 + KeepDays）、推界面。

分类这块我们做得比两家都正 —— AlarmCategory 就是 ALCD 的 1~8 全套（JK 只有 3/4/5 三档），
E30Element 的 S5F1 + going-on / going-off 事件按 GEM 要求发了。

但报警之后，全系统只发生这五件事：
  1. 推客户端报警栏 / 实时报警页
  2. SystemModule 每拍算 HasAlarm / HasWarning -> 驱动三色灯
  3. E30 发 S5F1、EDA 采集
  4. TankElement 自己看 HasAlarm 进 Error（全仓唯一一个）
  5. 动作失败 -> ModuleRoutine 失败 -> 模块落 ModuleState.Error
     （这是动作失败导致的，不是报警导致的）

没有的：报警 -> 关输出、报警 -> 停 Job、报警 -> 停投片、报警 -> 整机进 Error、
按级别或分类分派动作。AlarmLevel 四档的注释写着"后续会根据等级做相应动作"，还没做。
调度只看 station.State == ModuleState.Error 跳过那个站，从不查报警表。

================================================================================
二、两层划分
================================================================================

"报警之后做什么"不是一件事，是两层。前道设备重第二层，后道设备重第一层。

【第一层：动作某一步失败了怎么收场】
    RETRY / IGNORE / ABORT 属于这层。CTC 的 jobstop / jobabort、"中止后冲洗再下线"也属于这层。
    共同点是都挂在动作步骤上 —— 有动作在跑才谈得上。

【第二层：条件触发的联动动作】
    漏液 -> 关那组阀；高速旋转掉真空 -> 停卡盘 + 关药液阀 + 中止工艺。
    这层跟有没有动作在跑无关，每个扫描拍判一次。
    JK 的 Value.int、CTC 的 PLC 分级报警数组都是这层。

★ 本次做第二层。第一层以后做，现在给它留口子（见第四节）。

为什么先做第二层：35021 用得上；是我们对比下来最硬的缺口（出事现在真的什么都不做）；
不碰 ModuleRoutine，改动面小。

【前道 / 后道的分野】
    前道（Fab 里的刻蚀、薄膜、清洗、光刻）：24h 少人运行、全程 EAP 托管；一盒 25 片货值高，
    更要命的是 Q-time，片卡在腔里等人等废了。所以出事必须自己收场：关危险输出 -> 把在制片
    救出来 -> 这个腔下线 -> 别的腔照跑 -> 报给 Host 让它决定 Job。全程不问人。

    后道（封装、划片、固晶、测试）：设备旁边就站着人，单片价值低、节拍快，机械重复动作多、
    传感器误报率高，"再来一次"往往真能解决；很多后道机台压根没接 Host。
    所以停下来问人是最划算的。

    我们这台（35021 清洗机）按前道走，默认不开"问人"。
    但平台两种都要支持 —— RETRY/IGNORE/ABORT 做成可选能力，机型想开才开。


================================================================================
三、第二层设计（本次要做的）
================================================================================

一句话：报警报出的那一刻，抛给它所属的模块和整机，各自按 Level 收场；
       报警没清掉之前，危险输出每拍压着不让人打开。


------------------------------------------------------------
3.1 怎么抛
------------------------------------------------------------

新接口 IAlarmHandler，只有一个方法 OnAlarm(AlarmItem)。
不加 [Ioc]（容器登记靠 [Ioc] 特性筛，不加就不进容器）—— 它是顺元件树找的，不从容器取。

装配时（ElementLoader.AssignFullPath 那趟递归）顺手给每个元件存一个"往上最近的
IAlarmHandler"引用，跟现在传 modulePath 一样的做法。不用加 Parent 反向边。

RaiseAlarm 第一次报出时（现有去重逻辑保证不重复）抛两处：
    ① 往上最近的那个 IAlarmHandler
    ② 整机（经 ISystemAccess）
    两个是同一个时只抛一次。

★ 不一层一层往上抛。中间层元件（摆臂、卡盘）不设收点 —— 实际重写 OnAlarm 的只会是模块
  和 Safety，一层层抛等于给出一堆没人重写的空虚方法，而且"处理散在多层"以后排查要一级级找。
  中间层真想自己处理，让它在自己的 OnScan 里查 HasAlarm（现成的），或者由模块转给它。

★ 报警清除不往上抛。按"不自动恢复"的设计，清掉的时候父元件没事可做。真需要了再加。


------------------------------------------------------------
3.2 收点规则
------------------------------------------------------------

    报警来自                    收到的
    ------------------------    ----------------------------
    Chamber1.Door.Opened        Chamber1 + 整机
    Safety.Leak1                Safety   + 整机
    整机自己下面的元件          整机（同一个，只调一次）

两个相关的代码事实：
  - LogModule 算的是 machine.xml 第一层那个节点（ElementLoader 里定死后一路往下传），
    所以 Chamber1 下面气缸的 LogModule 是 "Chamber"（分组节点），不是 "Chamber1"。
    日志要的是这个两层名字，报警收点要的不是 —— 所以收点必须另算（用 IAlarmHandler 判据）。
  - Safety 和 System 在 machine.xml 里是平级的顶层节点，Safety 自己就是一棵树的根。
    所以"安全类报警写在安全元件里"天然成立，不用特殊照顾。

继承链（谁是"模块"、谁是"整机"）：
    ElementBase
    └─ BaseStateElement                    有状态机 + 能跑 ModuleRoutine
       ├─ SystemModule : ISystemModule      <- 整机。注意它不是 IModule
       └─ BaseModule   : IModule            <- 真正的"模块"
          ├─ BaseRobotModule                Robot1
          └─ BaseTransferStationModule
             ├─ BaseChamberModule           Chamber1
             └─ BaseLoadPortModule          LoadPort1


------------------------------------------------------------
3.3 四档动作（按 Level，不按 Category）
------------------------------------------------------------

★ Category 只上报 Host（ALCD）+ 界面显示，不参与任何控制逻辑；动作只看 Level。
  依据：ALCD 在标准里本来就是上报用的分类码，标准从没说它要驱动设备行为；JK 也是这么用的
  （级别映射 ALCD 给 Host、界面上色，动作一律另走互锁表）。
  这样也省掉一个 4×8 的二维矩阵。

    Level       平台默认动作                                    谁定
    ---------   --------------------------------------------    --------------------
    Warn        只报，不动                                      平台写死
    Light       当前动作做完后进 Error（模块空闲就立即进）      平台兜底，项目可改
    Heavy       立即 AbortByHost + 进 Error                     平台兜底，项目可改
    Fatal       整机 Abort，停所有模块                          平台写死

★ Light 和 Heavy 的区别只在"等不等"。
  Light 实现成"延迟进 Error"的好处：调度一行都不用改 —— 它现在就在判
  station.State == ModuleState.Error 跳过，模块做完这片进了 Error，自然就不再派活，
  正好是 CTC 的"做完这片再下线"。实现上只是 BaseStateElement 记个标志，
  CompleteRoutine 落状态时判一下。

★ 具体每档做什么是项目策略，平台不写死。但 Light / Heavy 平台还是要给个默认兜底，
  防静默失效：机型万一忘了写处理，重报警就变成"只亮个灯、设备照跑"。
  机型重写 OnAlarm 就能换掉。

平台和机型的分界线在"通用动作 vs 具体输出"：
  - 平台按 Level 做通用的那部分（中止动作、进 Error、挡新活、整机联动），全平台一套
  - 机型在 OnAlarm 里加自己那部分（关哪几个阀、停哪个泵），基类不猜

机型写法（想在默认之上加）：

    protected override void OnAlarm(AlarmItem alarm)
    {
        base.OnAlarm(alarm);

        // 重报警：药液阀泵一律关掉
        if (alarm.Level >= AlarmLevel.Heavy)
        {
            CloseChemicalValves();
        }
    }

想完全自己来，不调 base.OnAlarm 就行。

★ 整机状态要守住已定设计（decisions.md 381 / 385）：
  单个模块报警不改整机状态（Heavy 只停本模块，整机不动）；
  Safety -> 整机 Error 这条路径是当初留着要接的，Fatal 才动整机。


------------------------------------------------------------
3.4 持续互锁（不是一次性触发）
------------------------------------------------------------

模块 OnScan 每拍问一次"我名下有没有 Heavy 及以上的报警"，有就调 ApplySafeOutputs()
（虚方法，机型写自己的）。写 DO 幂等，每拍写一遍就压住了。

为什么要持续，不能只在报出时关一次：
    一次性关掉之后，人在手动页上点一下就能把阀再打开，等于没关。
    CTC 对比里它唯一硬压我们的几条中就有"持续互锁"。
    而且持续反而更好写 —— 不用记"我处理过没有"，照着报警状态每拍写一遍就行。

为此 IAlarm 加一个 HasAlarmUnder(path, minLevel) —— 返回 bool 就够，不用返回列表，最便宜。

★ 人工复位后不自动恢复输出。
  复位时把这些输出的目标状态一并归到安全位，撤掉压制的瞬间底下那条"开"的指令不会冒出来。
  场景：腔体漏液 -> 联动关了药液阀、停了泵（这期间每拍强制写"关"，手动页点也开不了）。
  人擦干净、查完管路，点复位，报警清掉 —— 就在清掉的那一拍压制撤了。
  如果自动恢复，阀会回到报警之前的样子（那会儿工艺正开着药液阀，它就自己又开了），
  可人的手可能还在腔里。所以不恢复，要再跑得人主动去点初始化。

  这跟现有规则配得很顺：我们的报警是人工复位才清、条件消失不自动清。
  所以人点复位时如果药液还在漏，下一拍联动会立刻再触发、再关一遍 —— 这正是想要的。

  "抛"和"查"两个都留，各管一半：
      抛（OnAlarm）        报出那一刻，立即关危险输出 + 中止动作
      查（HasAlarmUnder）  每拍确认，持续压着这些输出


------------------------------------------------------------
3.5 线程规矩
------------------------------------------------------------

★ OnAlarm 里只许做两件事：写安全输出、调 AbortByHost（或置延迟 Error 标志）。
  复杂判断、状态迁移一律放各自的 OnScan。

原因：报警不全在扫描线程上报。气缸超时、DI 判断在元件自己的 OnScan 里（最理想 ——
抛上去就是同一个线程、同一拍处理完），但驱动重连线程、RPC 线程也会报警。
定这条规矩后，抛上来做的两件事本身都是线程安全的（写 DO 幂等，AbortByHost 里有
_terminalGate 锁；模块侧用 RoutineGate，C# 的 lock 同线程可重入，动作步骤里报警也不会死锁）。

每个模块自己的扫描线程 10 ms 一拍（ElementBase.ScanIntervalMs），
关输出走 OnScan 完全来得及（JK 的互锁引擎也是每拍判）。


------------------------------------------------------------
3.6 跨模块（腔体报警影响别的模块）
------------------------------------------------------------

拆成三种，只有第三种需要新东西：

a) 腔体出事，别人只是不能用它了
   腔体进 Error -> 调度自动跳过它（SchedulerElement 已经在判）。
   已经有了，不用做，而且这是绝大多数情况。

b) 安全类，影响全局
   漏液、急停。这其实不是"腔体影响别人" —— 它本来就是整机级的事，
   写在整机 / 安全元件里，由它停所有腔体。

c) 真正点对点：腔体 A 出事要停供液 Tank B
   归整机，不让腔体去调 Tank。
   理由：腔体不该认识 Tank。模块之间一旦能直接调，机型一多就织成一张网 ——
   CTC 那 516 处客户名 if 就是这么长出来的。整机是唯一知道全局的那一层，
   跨模块的规则放一处，看得全、改得动。

   ★ 不为它做通用机制（依赖声明、配置联动表那种）。等真有这个需求了，
     在整机里直接写那几行 if。几行 if 看得懂，通用机制看不懂。


================================================================================
四、给第一层留的口子
================================================================================

四条，现在就定好，将来不返工：

1. 停动作一律走已有的 ModuleRoutine.AbortByHost(reason)，不另写一套"强行把模块掰到 Error"
   的捷径。第一层将来加"等人决策"态，这条路不用动。

2. 关输出不走动作框架，直接写 DO。关危险输出是立即的，不能排队等动作调度；
   中止动作才走框架。两件事两条路，第一层进来也不会混。

3. 第一层真正要加的是 RoutineState 多一个"等人"态（WaitingDecision）。
   第二层完全不碰 RoutineState，等于天然兼容。
