维护说明

一句话理解

事件总线 EventBus —— 进程内 + 跨进程统一的发布订阅

业务代码永远只跟 EventBus 打交道，它有两个静态方法：

EventBus.Send<T>(message, token);      // 发布
EventBus.Register<T>(token, handler);  // 订阅，返回 IDisposable 用于注销

所谓"进程内"和"跨进程"，对写代码的人来说没有任何区别——后端 Send、前端 Register，中间的 gRPC 传输、断线重连、UI 线程投递全部由基础设施自动完成。四种场景一张表看清：

场景谁发布谁订阅是否跨进程
A. 后端自己订阅自己发布后端 EventBus.Send后端 EventBus.Register否
B. 前端自己订阅自己发布前端 EventBus.Send前端 EventBus.Register否
C. 前端订阅后端（主场景）后端 EventBus.Send前端 EventBus.Register是（自动桥接）
D. 前端发往后端（上行）前端 RemoteEventBus.SendToServer后端 EventBus.Register是（一元调用）
对应实现：xyz.Core/Shared/xyz.Utilities（EventBus）· xyz.Service/Events（服务端桥）· xyz.Client.DataModels/Events（客户端流泵）

整体架构

每个进程各有一条进程内静态总线，gRPC 服务端流当水管

每个进程各有一条进程内的静态总线；后端到前端由一条 gRPC 服务端流当作"水管"，两端各有一个基础设施组件负责灌水和接水：

━━ 进程内：直接方法调用，同一对象引用，不经序列化 ══ 跨进程：信封（JSON）经 gRPC 流传输

三个使用前提都已经接好线，直接用即可：后端 GrpcHost 已 MapGrpcService<EventService>()；前端 App.OnStartup 已 GrpcClientFactory.Initialize() + RemoteEventBus.Initialize()。

定义消息

消息 = 普通 class / record，token = 字符串实例名

消息就是普通的 class 或 record，必须放在 xyz.Shared（DTO 目录旁）——因为跨进程时两端都要能序列化/反序列化它：

// xyz.Core/Shared/xyz.Shared/Messages/LoadPortMessages.cs
namespace xyz.Shared.Messages;

/// LoadPort 状态变化（状态类消息，推荐 record）
public sealed record LoadPortStateChanged(LoadPortDto State);

/// 操作员提醒（发生类消息示例）
public sealed record OperatorAttention(string Module, string Reason);

token 是什么

token 是一个普通字符串，用来区分"同一种消息的不同实例"——比如两台 LoadPort 用同一个消息类型，token 分别为 "LoadPort1"、"LoadPort2"，互不串扰。路由键 = （消息类型全名 + token），两者合起来唯一定位一条消息通道。token 省略（空串）表示该类型的全局消息，所有未指定 token 的订阅者都能收到。

场景 A：后端自己订阅自己发布 进程内

模块之间解耦：发布方完全不知道谁在听

典型用途：模块之间解耦。例如 LoadPortManager 轮询到状态变化后发布，同进程的报警模块、日志模块、调度模块各自订阅——发布方完全不知道谁在听。

后端 xyz.Service —— 模块 A：发布（如 LoadPortManager 轮询循环里）
EventBus.Send(new LoadPortStateChanged(snapshot), "LoadPort1");

后端 xyz.Service —— 模块 B：订阅（如 AlarmService 构造/初始化时）
EventBus.Register<LoadPortStateChanged>("LoadPort1", m =>
{
    // m 就是发布的那个 record，同一个对象引用，不经序列化
    if (m.State.State == ModuleState.Error) RaiseAlarm(...);
});
即使订阅发生在发布之后，也能立即收到该键最后一条留存消息——后端启动顺序不同步也没关系，晚初始化的模块照样拿到当前状态。

场景 B：前端自己订阅自己发布 进程内

客户端内部各页面/组件之间通信，不经过后端

典型用途：客户端内部各页面/组件之间通信，不经过后端。例如配方页面选了配方，标题栏、参数页都要刷新。

前端 xyz.Client —— 配方页面：发布
EventBus.Send(new RecipeSelected(recipeId));   // 不传 token = 全局消息

前端 xyz.Client —— 任意其他页面/控件：订阅
EventBus.Register<RecipeSelected>(m =>
{
    SelectedRecipeId = m.RecipeId;   // 直接改绑定属性
});
前端 EventBus.Send 的消息只在本进程内流转：不会传到后端，也不会传到其他客户端。进程内 Send 在调用线程同步回调——在 UI 线程发就 UI 线程收，在后台线程发就后台线程收。

场景 C：前端订阅后端 跨进程主场景

后端轮询硬件/模块 → 发布状态 → 前端界面实时刷新

这是整套东西存在的意义：后端轮询硬件/模块 → 发布状态 → 前端界面实时刷新。两端的写法和场景 A、B 完全一样——发布端不知道有没有人订阅、订阅端不知道消息从哪个进程来。

① 后端发布（与场景 A 逐字相同）

后端 xyz.Service —— LoadPortManager 轮询到状态变化
EventBus.Send(new LoadPortStateChanged(snapshot), "LoadPort1");

后端订阅者（场景 A）与前端订阅者会同时收到，互不影响。

② 前端订阅（与场景 B 逐字相同）

前端 xyz.Client.Manual —— LoadPortManualViewModel
public override void Init()
{
    EventBus.Register<LoadPortStateChanged>("LoadPort1", m =>
    {
        // 回调已在 UI 线程（RemoteEventBus 统一投递），可直接改绑定属性
        StateName = m.State.StateName;
        IsConnected = m.State.IsConnected;
    });

    EventBus.Register<LoadPortStateChanged>("LoadPort2", m => { ... });
}
跨进程订阅免费获得三个保障：
① 晚注册补发——VM 在流泵连上之后才 Init 也没关系，Register 时立即拿到当前状态；
② 断线自动重连——后端重启后 3 秒内自动重连，重连成功即重放所有留存消息，界面自动恢复到最新状态；
③ 回调必在 UI 线程——不需要任何 Dispatcher 代码。

③ 连接状态灯（可选）

界面顶部的通讯状态灯可直接绑定 RemoteEventBus：

前端 —— 订阅连接状态变化（ConnectionChanged 也在 UI 线程触发）
RemoteEventBus.ConnectionChanged += online => IsOnline = online;
// 或直接轮询属性：RemoteEventBus.IsConnected

场景 D：前端发往后端（上行）跨进程

前端主动通知后端某件事（注意：不是命令！）

前端主动通知后端某件事（不是命令！），用 RemoteEventBus.SendToServer。消息进入后端进程内总线，后端按场景 A 的写法订阅即可：

前端 —— 上行发布
RemoteEventBus.SendToServer(new OperatorAttention("LoadPort1", "料盒未到位"));

后端 —— 正常订阅（与场景 A 相同）
EventBus.Register<OperatorAttention>(m =>
{
    Logger.Warn($"操作员提醒: {m.Module} {m.Reason}");
});
上行的特点：① 默认不留存（发生类消息语义），晚注册的后端订阅者不会收到历史；② 不回声——不会广播给其他客户端；③ 后端不在线时静默丢弃，需要确认送达的业务应由后端回发一个事件确认。

线程与回调

四条路径各在哪个线程回调、能否直接改绑定属性

路径回调所在线程能否直接改绑定属性
进程内 Send → Register（前端）Send 的调用线程UI 线程发就能；后台线程发就不能
进程内 Send → Register（后端）Send 的调用线程（多为轮询线程）—（后端无 UI，注意被订阅方自己的线程安全）
跨进程：后端 Send → 前端 RegisterUI 线程（RemoteEventBus 投递）能，随便改
跨进程：前端上行 → 后端 RegistergRPC 线程池线程—（注意模块内加锁）

留存语义（retain）

状态类消息默认留存补发；发生类消息显式关掉

Send 默认按状态类消息处理：每个（类型 + token）键保留最后一条，用于——

  • Register 补发：订阅时立即收到当前值（晚初始化的模块/VM 不吃亏）
  • 重连重放：客户端断线重连后立即恢复全部最新状态

"发生了某件事"类的消息（日志、一次性通知、按钮点击通知）不适合补发，发布时显式关掉留存：

// 状态类（默认）：留最后一条，新订阅者补发
EventBus.Send(new LoadPortStateChanged(snapshot), "LoadPort1");

// 发生类：只给当时在线的订阅者，不留存、不补发
EventBus.Send(new OperatorAttention("LoadPort1", "料盒未到位"), retain: false);

约定与红线

命令绝不走事件通道；消息类放 xyz.Shared；token 用稳定业务名

命令绝不走事件通道。Load / Unload / Home 这类需要下发到硬件、需要知道成败的"命令"，必须走普通 gRPC 一元调用（如 ILoadPortService.InvokeActionAsync）。事件通道是单向通知：不保证送达时刻、没有返回值、没有错误回传。用事件发命令 = 丢命令 + 无法报错。
  • 消息类放 xyz.Shared——两端共用一个类型；类型全名是路由键的一部分，两端版本要一起发版。
  • token 用稳定的业务名——模块名（"LoadPort1"）、页面名等，不要用 GUID 这类每次变化的值（留存会失效）。
  • 订阅回调里不要做长活——跨进程回调在 UI 线程，长活会卡界面；重的活丢 Task.Run 或后台队列。
  • 注销：Register 返回 IDisposable。跟进程同寿命的模块/单例 VM 不需要注销；临时订阅（如弹窗页面）用完记得 Dispose，否则回调泄漏。
  • 排查丢消息：订阅 EventBus.DeadLetter（反序列化失败、订阅者回调抛异常都会触发，带着信封和异常）。

本文档如何扩充 —— 给未来往里加主题的人

这个页面是单文件的文档站：左侧是一个大菜单，一个主题 = 一个可折叠分组，组内每一小节就是右侧的一"页"。未来要介绍新东西（权限系统、模块开发、驱动开发、报警体系……）时，加一个分组 + 对应的页即可。

加一个新主题的三个步骤

  1. 在 <nav> 里复制顶部的"主题组模板"注释，改分组标题（建议带个 emoji 图标）；
  2. 在 <main> 里为每个小节添加 <section class="page" id="...">，id 与菜单项的 data-target 一致；
  3. 无需改任何 JS —— 页面切换、上一节/下一节、地址栏锚点都是自动生成的。

约定

  • 小节 id 用主题前缀（事件总线用 eb-），避免未来冲突；
  • 代码示例必须对应真实实现的 API，注明文件路径；
  • 纯离线：不引外部字体/脚本/样式，车间断网环境可直接打开。
